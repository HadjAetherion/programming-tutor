## 3. STAR 故事库（面试问答的核心弹药）

准备 4 个故事，每个能讲 2-3 分钟。**结构**：情境 → 任务 → 行动 → 结果。

### 故事 1：限流导致四个 Agent 只有一个成功（推荐主讲）

**S**：系统上线后测试发现，提交错误代码后只有"学习规划"有内容，另外三个模块空白。

**T**：定位原因并修复，且要保证在免费额度下系统仍可用。

**A**：
1. 查数据库 `llm_call_log`，发现只有 planning 有成功记录 → 说明其他三个调用失败
2. 用 curl 直连智谱 API 复现，拿到 HTTP 429 "账户已达到速率限制"
3. 判断是并发问题，先把并行请求改为 `Semaphore(1)` 串行 → 仍失败
4. 进一步发现限流是**分钟级窗口**，短退避的所有重试都落在同一窗口内空转
5. 改为**全局冷却**：收到 429 记录恢复时间点，后续请求在过闸前等待；退避 10s 起逐次加倍，最多 4 次

**R**：四 Agent 链路恢复；同时认识到本地端侧模型不受限流约束，这直接推动了"大小模型路由"的设计。

**可延伸的问题**：这样做会让 `latency_ms` 包含冷却等待时间，所以我在看统计时区分了"墙钟延迟"和"模型推理延迟"。

### 故事 2：LLM 全部成功，前端却报"诊断失败"

**S**：日志显示某次诊断四次调用全部成功、总耗时约 2 分 20 秒，但前端显示"诊断辅导获取失败"，且结果没有落库。

**T**：解释"成功却失败"的原因。

**A**：
1. 对比时间戳发现：Python 侧总耗时 140s，而 Go 的 HTTP 客户端和前端 axios 超时都是 120s
2. 结论：LLM 调用全部成功，但响应在超时之后才返回，结果被丢弃
3. 把两端超时统一放宽到 300s，同时给 LLM 加 `max_tokens` 限长缩短生成时间

**R**：问题消失。**教训**：多进程链路里，超时必须端到端一起考虑，不能只调一侧。

### 故事 3：规划 Agent 永远输出空白

**S**：修复超时后，规划 Tab 依旧空白，但 `llm_call_log` 显示 planning 调用成功。

**T**：找出为什么"成功调用"却解析不出内容。

**A**：
1. 查日志发现 planning 的 `completion_tokens` 恰好是 **1024**——正是 `max_tokens` 上限
2. 判断输出被截断，JSON 不完整导致解析失败，降级为空
3. 把 `max_tokens` 改成按 Agent 配置，规划 Agent 放宽到 1536

**R**：规划内容正常，并且开始正确引用学情薄弱点。

### 故事 4：Java 的 19 个概念只入库了 8 个

**S**：为支持多语言，给知识图谱种子数据加了 Python/Java/C++ 概念，但查库发现 Java 只有 8 个节点。

**T**：找出为什么数据"少了一半多"。

**A**：
1. 对比发现缺失的都是与 Go 已有的同名概念（"递归""异常处理""循环"）
2. 根因：`knowledge_nodes` 主键是 `name` 单列，种子用 `ON CONFLICT (name) DO NOTHING`，重名的被直接忽略
3. 写迁移把主键改为 `(language, name)` 复合主键，并把边、标注、掌握度的外键同步改为带 language 的复合外键

**R**：四语言概念完整入库（88 节点）。**收获**：多语言支持不是"加个字段"，而是要重新审视所有键设计。

## 4. 面试高频问题与回答要点

### 关于架构

**Q：为什么拆成 Go + Python 两个服务？**

> 判题需要频繁起容器、并发处理，Go 更合适且已有 OJ 基础；LLM 编排与客户端生态在 Python 更成熟。拆开的代价是多一个进程和一次 HTTP 跳转，收益是两边都能用最合适的工具。如果规模大了，我会考虑把诊断改成消息队列异步化。

**Q：为什么要四个 Agent？一个 prompt 不行吗？**

> 一个 prompt 同时做"判对错+夸代码+给建议"输出不稳定，而且职责没法独立演进、独立评估。分开的好处：① 每个 Agent 的输出结构可以单独优化；② 能独立降级；③ 审查能明确"不判断对错"，反馈能明确"不给完整答案"——这些边界是在 prompt 里显式约束的。

### 关于路由（核心考点）

**Q：路由规则是怎么定的？依据是什么？**

> 依据是"教学任务的异质性"：编译错误只需定位问题，短代码审查只需规范性检查，这类任务端侧 7B 模型够用；而逻辑推理、多维度规划需要更强的云端模型。所以规则是：诊断遇到编译错误且代码短 → 端侧；审查短代码 → 端侧；反馈是直接提示策略 → 端侧；其余 → 云端。

**Q：怎么证明路由有效？**

> 每次调用都写 `llm_call_log`（角色、层级、模型、延迟、token、成本）。按 tier 聚合可以看到：端侧 1.3~12s、云端 23~94s；组间对比每次诊断 4208 vs 8521 Token、84s vs 188s。正式实验用 `ROUTER_FORCE_TIER=cloud` 做对照组。

**Q：为什么不用学习型路由？**

> 三个现实原因：让 LLM 决定路由本身就多了一次调用，与省钱矛盾；规则可解释、能写进论文逐条论证；小样本实验下学习型路由不可靠。未来可以用历史调用日志训练轻量分类器，这是合理的改进方向。

### 关于 Agent 工程

**Q：Prompt 里怎么保证 Agent 不"越界"？**

> 两层：① system prompt 里显式写边界，比如审查 Agent 写"正确性诊断由另一个 Agent 负责，你不要越界分析对错"；② 输出用 JSON schema 约束字段；③ 服务端对 LLM 输出的概念做白名单过滤，只保留存在于知识图谱的概念。

**Q：LLM 返回不合规怎么办？**

> 解析层做容错：兼容 ```json 包裹、前后多余文字、截断；解析失败降级为纯文本摘要而不是报错。另外用 `max_tokens` 按 Agent 配置避免截断——规划 Agent 就是因为 1024 被截断过。

**Q：多个 Agent 怎么共享上下文？**

> 用一个 `AgentContext` 作为显式协议：上游写 `diagnosis_result`、`review_result`，下游读。不用全局变量，是为了让数据流可推理、可测试。

### 关于可靠性（加分项）

**Q：怎么做降级？**

> 三层：① 网关层，某层级失败自动回退另一层级；② 编排层，单 Agent 异常时返回中文降级文案，其他模块照常；③ 前端层，旧数据做字段兜底。另外数据库不可用时诊断主流程仍能跑（成本日志降级），知识图谱读不到时回落到内置词表。

**Q：异步任务怎么处理？**

> 判题通过后要更新掌握度，但这是辅助数据，不能拖慢判题响应，所以用 goroutine fire-and-forget，5s 超时，失败只记日志。**关键细节**：必须用 `context.Background()` 而不是请求的 ctx，因为响应返回后请求 ctx 已被取消。

### 关于数据与算法

**Q：掌握度算法为什么选 EMA？**

> BKT 要按题目估计 guess/slip，DKT 要大量序列数据，本科实验规模下都不可靠。EMA 参数少（两个系数）、可解释、能一条 SQL 实现。失败按比例衰减、通过按比例饱和，行为符合直觉。局限是不建模题目难度和遗忘。

**Q：知识图谱规模多大？前置依赖边用在哪？**

> 88 个概念节点、87 条边。**诚实说明**：边目前主要用于建模与论文表达，代码里还没有基于前置依赖做"补基础"的推荐逻辑——这是我明确知道可以继续做的方向。

### 关于局限（主动承认，非常重要）

**Q：这个项目有什么不足？**

按这个顺序说（表现出清晰的自评能力）：

> 1. **沙箱隔离偏弱**：目前只有 `--rm` + 挂载 + 超时，没有 `--network none`、内存/CPU 限制、非 root 运行；题目表有 `time_limit_ms` 字段但判题用的是硬编码超时。
> 2. **诊断是同步长请求**：用户要等，而且后端没有同一提交的并发互斥，重复点击会重复调 LLM。应该改成任务化 + 轮询/SSE。
> 3. **路由预算计数是进程内全局变量**：多 worker 下不准，应该外置到 Redis。
> 4. **判题 fail-fast**：遇到第一个失败就停，不是完整评测机；输出比对只有 TrimSpace，没有浮点容差。

## 6. 项目讲解的三个时长版本

### 1 分钟版（自我介绍里用）

> 我做了一个面向编程学习的多智能体诊断系统。学生提交代码后，四个 Agent 分别做错误诊断、代码审查、自适应辅导和学习规划，通过两阶段并行编排降低响应时间。核心设计是规则式路由——按任务异质性把简单任务交给本地小模型、复杂任务交给云端，实测 Token 降 50%、延迟降 55%。另外做了四语言知识图谱和掌握度模型，让规划能针对学生薄弱点。技术栈是 Go + Python + Vue。

### 5 分钟版（面试主答）

按这个结构：
1. **背景与问题**（30s）：OJ 只判对错；直接接大模型成本高、限流、建议不个性化
2. **架构**（1min）：三层，为什么这么拆
3. **核心设计 1：四 Agent 协作**（1min）：职责边界、两阶段并行、上下文协议
4. **核心设计 2：大小模型路由**（1.5min）：规则表、依据、回退、效果数据
5. **核心设计 3：学情闭环**（1min）：EMA、图谱约束、规划引用薄弱点
6. **结果与局限**（30s）：数据 + 主动说两个局限

### 15 分钟版（技术面深入）

在 5 分钟版基础上加：
- 限流故障的完整排查过程（故事 1）
- 沙箱实现细节（编译一次、每用例一容器、解释型语言的语法预检）
- 数据库设计取舍（JSONB、复合主键的踩坑）
- 前端加权平均与配色校验这类细节
