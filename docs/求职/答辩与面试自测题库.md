## 第一部分：架构与整体（1-6）

**Q1. 这个项目解决什么问题？为什么不能直接接一个大模型？**

<details><summary>答案</summary>

OJ 只能判对错，不能回答"错在哪、怎么改、下一步学什么"。直接接大模型有三个现实问题：
1. **成本与限流**：云端免费额度并发配额低（实测并行 2 个请求即 429），响应可达数十秒甚至更久；
2. **缺乏个性化**：模型不知道学生历史薄弱点，建议千人一面；
3. **职责混杂**：一个 prompt 同时做"判对错 + 夸代码 + 给建议"，输出质量不稳定。

本项目用四个职责分离的 Agent 分工，再用规则路由把低阶任务交给端侧小模型，解决成本与延迟问题。
</details>

**Q2. 为什么拆成 Go / Python / Vue 三层？**

<details><summary>答案</summary>

- **Go**：判题需要频繁创建容器、并发处理请求，Go 的进程模型与标准库更适合；且已有 OJ 基础。
- **Python**：多智能体编排（asyncio）、LLM 客户端生态成熟，迭代快。
- **Vue**：组件化、Monaco 与 Element Plus 生态。

**如果不拆**：Go 里做 LLM 编排会很难维护（Go 的异步与 LLM SDK 生态弱于 Python）；Python 里重写判题会丢掉已有基础。代价是多了一个进程和一次 HTTP 跳转。
</details>

**Q3. Go 和 Python 之间怎么通信？为什么用 HTTP 而不是消息队列？**

<details><summary>答案</summary>

进程内 HTTP（`backend/internal/diagnosis/client.go`），超时 300s。

用 HTTP 而不是 MQ：诊断是**同步请求-响应**语义（前端在等结果），MQ 需要额外的结果订阅机制；当前规模单机部署，HTTP 足够且调试简单。如果要做异步化，MQ 是更好的选择（这是可以讲的改进方向）。
</details>

**Q4. 一次提交到诊断展示，数据流经过哪些环节？**

<details><summary>答案</summary>

```
前端 submitCode
→ POST /submissions/submit
→ submission_handler.SubmitCode（校验语言 → Normalize → 判题 → 落库）
→ judge_service.Judge（Compile 一次 → 逐用例 Run）
→ 返回结果给前端
→ 前端发现 status !== ACCEPTED → POST /submissions/:id/diagnose
→ diagnosis_service → diagnosis.Client（HTTP，300s）
→ Python POST /api/v1/diagnose
→ orchestrator.diagnose（阶段一 gather → 学情更新 → 阶段二 gather）
→ 返回 → Go 存 submission_diagnosis → 前端 4 Tab
→ 若 AC：不诊断，走 mastery/record 异步强化
```
</details>

**Q5. 诊断为什么是同步长请求？有什么问题？**

<details><summary>答案</summary>

当前是同步请求（Go 客户端 300s、axios 300s），前端显示"约需 1-3 分钟"。

**问题**：① 用户必须等；② 后端**没有同一提交的并发诊断互斥**，重复点击会重复调用 LLM（浪费配额）；③ 请求可能被中间层断开。

**改进方向**：改成任务化——POST 返回 task_id，前端轮询或 SSE 推送。这是很自然的"下一版要做什么"。
</details>

**Q6. 你的项目有多少行代码？测试情况如何？**

<details><summary>答案（诚实回答）</summary>

Go 约 2955 行、Python 约 1793 行、前端约 3344 行，10 个数据库迁移脚本。

**测试**：初期没有自动化测试（开发期靠真实提交与数据库核验），**后期补充了 pytest 与 Go 测试覆盖核心纯函数**（路由规则、JSON 解析容错、干预策略、语言归一、EMA 边界）。

> 如果你还没补测试，如实说"目前以手工验证为主，正在补单元测试"，不要说"测试完善"。
</details>

## 第二部分：判题沙箱（7-12）

**Q7. 支持哪几种语言？各用什么镜像？**

<details><summary>答案</summary>

| 语言 | 镜像 | 源文件 |
|---|---|---|
| Go | `golang:1.22-alpine` | main.go |
| Python | `python:3.12-alpine` | main.py |
| Java | `eclipse-temurin:17-jdk-alpine` | Main.java |
| C++ | `gcc:12` | main.cpp |

> C++ 用 `gcc:12` 而非 `gcc:13-alpine`，因为官方 GCC 镜像**没有 alpine 变体**（踩过这个坑）。
</details>

**Q8. 新增一门语言要改几处？**

<details><summary>答案</summary>

代码层面**只需在 `spec.go` 的 `specs` map 登记一条**（镜像、源文件名、编译命令、运行命令）。

但完整支持还需要：① Python 侧 `base.py` 的 `LANGUAGE_LABELS`；② `knowledge.py` 的 `DEFAULT_CONCEPTS`；③ 知识图谱种子数据（该语言的概念节点）。共 4 处——这是"注册表驱动"设计的好处，也是它的边界。
</details>

**Q9. Python 不需要编译，为什么还有"编译阶段"？**

<details><summary>答案</summary>

为了**把语法错误正确归类为 `COMPILE_ERROR`**，与编译型语言行为一致。实现上：`CompileOut` 为空时，编译阶段执行 `python -m py_compile main.py`。

否则 Python 的 `SyntaxError` 会出现在运行阶段，学生看到的错误类型会和其他语言不一致，也会影响反馈 Agent 的干预策略选择（策略规则依赖判题状态）。
</details>

**Q10. 判题是怎么跑的？编译几次？起几个容器？**

<details><summary>答案</summary>

- **编译一次**：`Compile` 写临时目录 → `docker run` 编译，产物留在 bind mount 的 `/workspace`。
- **每个测试用例起一个新容器**：`Run` 循环里每例一次 `docker run`，输入通过 `sh -c "./program < input.txt"` 重定向。

**代价**：容器启动开销大（四语言实测单次提交 2-3 秒）。**改进**：常驻容器或批处理。
</details>

**Q11. 超时怎么实现的？阈值多少？**

<details><summary>答案</summary>

`exec.CommandContext` + `context.WithTimeout`：编译 **10s**、单次运行 **5s**。超时映射为 `TIME_LIMIT` / 编译超时。

**已知局限**：`problems` 表有 `time_limit_ms` / `memory_limit_mb` 字段，但判题**用的是硬编码 5s/10s，没有读题目配置**，也没有内存限制。
</details>

**Q12. 沙箱隔离够强吗？**

<details><summary>答案（主动承认局限）</summary>

**不够强**。当前只做了：`docker run --rm` + bind mount 临时目录 + workdir，代码文件权限 0600。

**缺失**：`--network none`、`--memory`、`--cpus`、`--pids-limit`、`--read-only`、非 root 用户运行。

**改进**：这些都是 Docker 现成参数，加进 `dockerArgs` 即可；生产环境还应该用 gVisor / Firecracker 一类更强隔离。这是答辩时主动说出来的加分点——**知道自己方案的边界，比假装完美更可信**。
</details>

## 第三部分：多智能体编排（13-19）

**Q13. 四个 Agent 各自负责什么？职责边界怎么划？**

<details><summary>答案</summary>

| Agent | 职责 | 边界 |
|---|---|---|
| 诊断 | 错误类型、根因、涉及知识点 | 不评价代码质量 |
| 审查 | 质量评分、亮点、问题清单 | **不判断对错**（prompt 里明确写了"正确性诊断由另一个 Agent 负责，你不要越界"） |
| 反馈 | 按干预策略生成辅导内容 | **不给完整正确代码** |
| 规划 | 学习步骤、下一题建议 | 依赖诊断 + 审查 + 学情 |

边界是在 prompt 里显式约束的，这是"多智能体"与"一个 prompt 做所有事"的核心区别。
</details>

**Q14. 为什么是两阶段并行，而不是全串行或全并行？**

<details><summary>答案</summary>

依赖关系决定：反馈需要诊断结论（才能选干预策略），规划需要诊断 + 审查（才能给完整建议）。

- **全串行**：4T 时间
- **两阶段并行**：诊断 ∥ 审查（1T）→ 反馈 ∥ 规划（1T）= 约 2T
- **全并行**：反馈拿不到诊断结果，规划拿不到审查结论

墙钟时间用 `perf_counter` 实测，与四次 latency 之和对比即可证明并行生效。
</details>

**Q15. Agent 之间怎么传递数据？**

<details><summary>答案</summary>

通过 `AgentContext`（`agents/base.py`）作为显式通信协议：上游 Agent 把产出写入 `ctx.diagnosis_result` / `ctx.review_result`，下游 Agent 读取。

**为什么不用全局变量**：显式契约便于测试与推理数据流；每个 Agent 的输入输出清晰可查。
</details>

**Q16. 某个 Agent 挂了会怎样？**

<details><summary>答案</summary>

三层降级：
1. **gateway 层**：某 tier 调用失败 → 回退另一个 tier
2. **orchestrator 层**：`_run_agent` 包 try/except，失败返回 `(None, None)`，用**中文降级文案**填充该块，整链不中断
3. **前端层**：`normalizeDiagnosis` 兜底旧数据

学生看到的是"该模块暂时不可用，请稍后重试"，其余三个模块正常。
</details>

**Q17. 学情更新为什么放在两阶段之间？**

<details><summary>答案</summary>

保证**规划 Agent 读到的薄弱点已包含本次失败的影响**。

如果放在最后，规划用的是"上一次诊断之后"的掌握度，那本次失败的信息就丢失了——而这恰恰是最该被规划考虑的信息。
</details>

**Q18. 干预策略是谁决定的？规则是什么？**

<details><summary>答案</summary>

**规则决定**，不是 LLM 决定（`decide_style`）：

| 判题状态 | 通过率 | 策略 |
|---|---|---|
| COMPILE_ERROR | 任意 | direct_hint |
| RUNTIME_ERROR | 任意 | socratic |
| TIME_LIMIT | 任意 | socratic |
| WRONG_ANSWER | ≥ 0.6 | socratic |
| WRONG_ANSWER | < 0.6 | scaffold |
| 其他 | 任意 | scaffold |

**教育学依据**：最近发展区——越接近正确，越适合高认知负荷的追问；差距越大越需要结构化支架。

**为什么不用 LLM 选**：规则可解释、可复现、无额外成本，小样本实验下更可信。
</details>

**Q19. LLM 输出不是合法 JSON 怎么办？**

<details><summary>答案</summary>

`_extract_json` 依次处理：```json 包裹 → 前后多余文字 → 取第一个 `{` 到最后一个 `}`；解析失败则**降级为纯文本摘要**，不抛异常。

**规划 Agent 曾真实踩坑**：输出恰好 1024 tokens 被截断导致 JSON 不完整 → 单独把 `max_tokens` 放宽到 1536。
</details>

## 第四部分：路由与模型网关（20-26）

**Q20. 路由决策器的规则是什么？**

<details><summary>答案</summary>

判定优先级：`ROUTER_FORCE_TIER` 强制 > 累计成本超预算强制 edge > 角色规则表。

| Agent | 条件 | 层级 |
|---|---|---|
| 诊断 | 编译错误 且 代码 ≤1500 字符 | edge |
| 审查 | 代码 ≤2000 字符 | edge |
| 反馈 | 策略 = direct_hint | edge |
| 规划 | 概念数 ≤2 且 审查分 ≥80 | edge |
| 其余 | — | cloud |

**依据是"教学任务异质性"**：编译错误只需定位、短代码审查只需规范检查，端侧小模型足够；逻辑推理与多维规划需要云端。
</details>

**Q21. 为什么用规则而不是让 LLM 决定路由？**

<details><summary>答案</summary>

1. **成本**：让 LLM 决定路由本身就是一次 LLM 调用，与省钱的目标矛盾；
2. **可解释**：规则能写进论文、能画成流程图、能逐条论证教学依据；
3. **稳定与延迟**：规则是常数时间，不会引入额外失败点；
4. **小样本实验可信**：学习型路由需要训练数据，本科实验规模下不可靠。

**可讲改进**：用历史 `llm_call_log`（角色、代码特征、层级、结果质量）训练轻量分类器——这是很好的"未来工作"。
</details>

**Q22. 端侧失败后回退，在哪一层做的？**

<details><summary>答案</summary>

**gateway 层**（`llm/gateway.py`）：`except` 捕获后 `fallback = "cloud" if tier == "edge" else "edge"`，调另一侧。

注意是**双向回退**——云端失败也会回退端侧。回退调用本身不再 try，若也失败则异常冒泡到 orchestrator，由 Agent 兜底处理。
</details>

**Q23. 429 为什么不能靠简单重试解决？你的处理是什么？**

<details><summary>答案</summary>

实测发现智谱免费模型的限流是**分钟级窗口**：短退避（1s、2s）的所有尝试都落在同一个限流窗口内，白白消耗重试次数。

**处理**（`llm/client.py`）：
1. 收到 429 设全局 `_rate_limit_until`（模块级变量），10s 起、逐次加倍；
2. 后续请求拿到并发闸后**先 sleep 到冷却结束**再发；
3. `MAX_ATTEMPTS=4`，可重试 `{429,500,502,503,504}`；
4. 云端并发闸 `Semaphore(1)` 串行。

**副作用（要主动说）**：`latency_ms` 记录的是**含冷却等待的墙钟时间**，不等于模型真实推理耗时。
</details>

**Q24. 为什么云端 Semaphore 是 1，端侧是 2？**

<details><summary>答案</summary>

云端免费额度并发配额极低（实测并行 2 个请求即被拒），所以串行化；端侧是本地 Ollama，能力受 GPU 限制但不受 API 配额约束，允许 2 个并发。

`Semaphore` 建在**客户端实例上**，所以云端与端侧互不阻塞。
</details>

**Q25. `ROUTER_BUDGET_YUAN` 是怎么实现的？有什么问题？**

<details><summary>答案</summary>

`_accumulated_cost_yuan` 是 `router.py` 的**模块级全局变量**，每次调用成功后累加成本；超过预算阈值则强制走端侧。

**问题（主动说）**：
1. 进程内全局，**多 worker 各自计数**，预算不准确；
2. 永不重置，长时间运行会一直锁在端侧；
3. 端侧成本为 0，所以"省钱"效果依赖云端单价配置。

**改进**：存 Redis / 数据库，按租户或时间窗口统计。
</details>

**Q26. `llm_call_log` 记录了哪些字段？有什么用？**

<details><summary>答案</summary>

`agent_role`、`model_tier`、`model_name`、`latency_ms`、`prompt_tokens`、`completion_tokens`、`cost_yuan`、`user_id`、`submission_id`。

**用途**：创新点③"成本-质量联合评估"的数据基础——仪表盘、统计分析脚本的成本/延迟对比全部由它聚合。这是项目里"可观测性"的落点。
</details>

## 第五部分：知识图谱与学情（27-32）

**Q27. 掌握度用什么算法？公式是什么？**

<details><summary>答案</summary>

EMA（指数移动平均）：

- 失败（诊断触发）：`m' = m × (1 − 0.3)`
- 通过（AC）：`m' = m + 0.4 × (1 − m)`
- 初始 0.5；`m < 0.4` 记一次薄弱

**性质**：失败按比例衰减（不会瞬间归零），通过按比例逼近 1（天然饱和，单次 AC 不会判定"掌握"）。
</details>

**Q28. 为什么不用 BKT 或 DKT？**

<details><summary>答案</summary>

BKT 需要按题目估计 guess/slip 参数，DKT 需要大量序列数据——本科实验规模下不可靠拟合。

EMA 参数少、可解释、可在 SQL 层一条 UPDATE 实现，且行为符合直觉。**承认局限**：它不建模题目难度，也不考虑遗忘曲线。
</details>

**Q29. 为什么知识图谱用复合主键 `(language, name)`？**

<details><summary>答案（真实踩坑）</summary>

最初 `knowledge_nodes` 主键是 `name` 单列，导致 **Java 的 19 个概念只入库 8 个**——因为"递归""异常处理""循环"等名字与 Go/Python 重名，`ON CONFLICT (name) DO NOTHING` 把后插入的直接忽略了。

修复：迁移 007 改为 `(language, name)` 复合主键，并把边、标注、掌握度的外键都改成带 language 的复合外键。

**这个问题很适合讲**：它说明"多语言支持"不只是加个字段，而是要把整个键设计重新考虑。
</details>

**Q30. LLM 输出了词表外的概念怎么办？**

<details><summary>答案</summary>

两道防线：
1. **提示词约束**：诊断 Agent 的 system prompt 里注入该语言的完整知识点列表，要求"只能从中选择"；
2. **服务端白名单过滤**：`_known_concepts` 只保留存在于该语言图谱的概念，防止外键报错与脏数据。

**为什么两道都要**：提示词不保证 100% 遵守，服务端过滤是兜底。
</details>

**Q31. 掌握度在什么时候衰减？**

<details><summary>答案</summary>

在**诊断时**（`on_diagnosis`），不在判题时——因为只有诊断才有概念标注（`concepts` 来自诊断 Agent）。

**副作用（主动说）**：学生提交失败但**没有点诊断**，掌握度不会变化。
</details>

**Q32. AC 后掌握度怎么强化？为什么只取 top-5？**

<details><summary>答案</summary>

判题 AC → Go 端 `go func` 异步 `POST /mastery/record`（5s 超时，fire-and-forget）→ Python `record_outcome` 取该题该语言标注概念中 `hit_count` 最高的 **5 个**做 EMA 增强。

**为什么 top-5**：题目可能积累很多概念标注，全增强会让无关概念也被强化；top-5 是"该题最核心概念"的近似。

**局限**：题目尚未标注概念时，AC 是 no-op。
</details>

## 第六部分：数据库与后端工程（33-37）

**Q33. 判题结果为什么用 JSONB 存？**

<details><summary>答案</summary>

四个 Agent 的产出结构异构（诊断是简单字段、审查是数组、规划是步骤列表）且会演进；拆成固定列会导致频繁改表。

`concepts` 单独抽成列是为了按知识点聚合（`problem_concepts`、掌握度都需要）。

**注意**：pgx 写 jsonb 要传 `string` 而不是 `[]byte`（会被当 bytea 报类型不匹配），这是真实踩过的坑。
</details>

**Q34. 提交列表怎么知道哪条已诊断？**

<details><summary>答案</summary>

`LEFT JOIN submission_diagnosis`，用 `CASE WHEN d.id IS NULL THEN false ELSE true END` 得出 `has_diagnosis`，前端据此显示"已诊断"标签。

用 LEFT JOIN 而非 EXISTS 子查询：一次查询即可，且能同时返回其他字段。
</details>

**Q35. 怎么保证学生看不到别人的数据？**

<details><summary>答案</summary>

所有按 ID 的查询都带 `user_id` 条件：`GetByIDAndUserID(ctx, id, userID)`；诊断读取带 `WHERE submission_id=$1 AND user_id=$2`。

JWT 中间件把 `user_id` 注入 gin.Context，handler 从 context 取，不信任请求体里的 user_id。
</details>

**Q36. 判题 AC 后的异步上报，为什么用 `context.Background()` 而不是请求的 ctx？**

<details><summary>答案</summary>

因为 goroutine 在 **HTTP 响应返回之后**才可能执行完，此时请求 ctx 已被取消，用它会立刻失败。

所以用 `context.Background()` + 自己的 5s 超时，并用 `go func(uid, pid int64)` **显式传参**避免闭包捕获循环变量。
</details>

**Q37. 为什么编译失败/答案错误返回 `(result, nil)` 而不是 error？**

<details><summary>答案</summary>

**业务结果与系统错误要分离**：
- 编译失败、WA、TLE、RE 都是**正常的业务结果**，应该返回给学生展示；
- 只有沙箱基础设施故障（Docker 不可用等）才是系统错误，返回 error。

这样 handler 层能清晰区分"要返回 200 + 结果"还是"返回 500"。
</details>

## 第七部分：前端（38-40）

**Q38. 诊断为什么在提交后不阻塞判题结果展示？**

<details><summary>答案</summary>

判题返回后**立即**展示判题结果（状态、用例、耗时），诊断在**之后**才发起（`loadDiagnosis`），并且只在 `status !== 'ACCEPTED'` 时触发。

`diagnosing` 标志防前端重复触发。axios 该请求单独设 300s 超时。

**局限**：这是前端防重入，**后端没有互斥**——同一提交重复点诊断会重复调用 LLM。
</details>

**Q39. 仪表盘的延迟对比为什么要"加权平均"？**

<details><summary>答案</summary>

后端 `GET /me/llm-stats` 返回的是**按 (角色, 层级) 聚合**的平均延迟；直接对各行取平均会让"调用次数少的组合"权重过高。

前端按 `calls` 加权：`Σ(calls × avg_latency) / Σcalls`，才是真实的整体平均延迟。这是一个容易被忽略但很见功力的细节。
</details>

**Q40. 图表为什么不用 ECharts？两种颜色怎么选的？**

<details><summary>答案</summary>

**不用 ECharts**：省约 1MB 依赖；条形图用 CSS 即可实现，更轻、可控。

**配色**：端侧 `#2a78d6`（蓝）、云端 `#eb6834`（橙）。做了色觉障碍模拟校验（ΔE 24.7，阈值 8）与对比度检查（均 ≥3:1）。

**第二编码**：每组数据配等价表格视图，颜色不是唯一区分手段；图表带 `role="img"` + `aria-label`。
</details>

## 附加：高频"压力题"与应对

### P1. "这个项目你用 AI 辅助了吗？"

**建议回答思路**（诚实且不贬低自己）：

> 用了。AI 在写代码和查 API 上帮了忙，但**架构怎么拆、路由规则怎么定、遇到限流和超时怎么定位、为什么选 EMA 而不是 BKT**，这些是我自己判断和验证的。比如 429 那次，是先查数据库日志发现四个 Agent 只有一个成功，再用 curl 直连确认是限流，才改成全局冷却——这类问题 AI 一次也给不出答案。

**核心**：把话题引到**判断与验证**上，这正是 AI 替代不了的部分。

### P2. "这个项目最难的地方是什么？"

**可选素材**（都是真实发生的）：
- 限流：并行请求全 429 → 定位到分钟级窗口 → 全局冷却
- 超时：LLM 全成功了但前端报"失败"，因为 120s 超时 → 放宽到 300s
- 截断：规划 Agent 输出恰好 1024 tokens → JSON 不完整 → 按 Agent 调 max_tokens
- 同名概念：Java 19 个概念只入库 8 个 → 复合主键

**推荐讲"限流"那条**：有数据、有排查过程、有修复、有副作用认知。

### P3. "如果给你更多时间，你会怎么改？"

按优先级：
1. **测试**：补全单元测试与集成测试（目前只覆盖核心纯函数）
2. **沙箱加固**：`--network none`、内存/CPU 限制、非 root、读题目配置的超时
3. **诊断异步化**：任务化 + 轮询/SSE，避免长请求与重复调用
4. **路由学习化**：用历史调用日志训练分类器
5. **状态外置**：预算计数移到 Redis

### P4. "你的路由策略效果如何证明？"

> 通过 `llm_call_log` 按 `model_tier` 聚合对比。开发期数据：端侧 1.3~12s、云端 23~94s（云端含冷却等待）；组间对比每次诊断 4208 vs 8521 Token、84s vs 188s。正式实验按协议招募被试重新采集。
</details>
