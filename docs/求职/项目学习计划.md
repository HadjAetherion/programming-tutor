# 项目学习计划：把它真正变成你能讲的自己的项目

**适用对象**：本项目作者本人
**目标岗位**：AI Agent 开发 / 大模型应用（后端融合）
**制定日期**：2026-11-17

---

## 0. 先明确一件事

"项目是你的"不等于"代码是你一行行敲的"。面试官和答辩老师真正检验的是三件事：

1. **你能不能不看代码画出架构、讲清数据流**
2. **你能不能解释每个关键设计为什么这样做、备选是什么、代价是什么**
3. **你能不能现场改它**——加一个功能、修一个 bug、加一个测试

第 1、2 项靠精读，第 3 项靠动手。本计划按这个顺序安排。

> **诚实原则**：不要声称做过没做过的事。面试官只要追问两层就能识破，代价远大于收益。本计划的目标是让你**真的会**，而不是"看起来会"。

### 任务 2：把 EMA 抽成纯函数并测试

当前掌握度计算写在 `_update_mastery` 里，和数据库操作混在一起，**没法测**。

**做法**：在 `knowledge.py` 顶部加

```python
def next_mastery(old: float, failed: bool, *, alpha_fail=ALPHA_FAIL, alpha_pass=ALPHA_PASS) -> float
```

让 `_update_mastery` 调用它，然后为它写测试（包括 0 和 1 的边界、连续失败的收敛趋势）。

**为什么这一步值得做**：它是简历上"可测试性重构"的真实例子，也是面试常问的"你怎么保证学情算法正确"。

### 任务 5：修复三个已知缺陷（★ 最高优先级，答辩必被问）

代码通读后发现三处**"设计上承诺了但实现没做到"**的地方。修好它们，既堵答辩漏洞，又能在简历上写"修复 xxx"。

#### 5.1 沙箱缺少资源限制（安全性）

**现状**：`sandbox/runner.go` 的 `dockerArgs` 只有 `--rm`、挂载、workdir。学生代码可以联网、吃满内存、开满进程。

**修复**：加上

```go
"--network", "none",        // 禁网
"--memory", "256m",         // 内存上限
"--cpus", "1",              // CPU 配额
"--pids-limit", "128",      // 防 fork 炸弹
```

> ⚠️ 先只加这几个稳妥的。`--read-only` 与 `--tmpfs` 会让 `/workspace` 写不进去，需要额外调整挂载方式，**改完必须四语言各测一次**。

**验收**：四语言提交正常代码仍 ACCEPTED；提交死循环仍 TLE 而不是拖垮机器。

#### 5.2 判题未使用题目的时间/内存限制（功能缺失）

**现状**：`problems` 表有 `time_limit_ms`、`memory_limit_mb`，模型也读出来了，但 `JudgeService` 用硬编码 5s/10s。

**修复思路**：把题目的 `time_limit_ms` 传给 `runner.Run`（函数签名加 `limit time.Duration`），同时改 `RunCode` 的调用点。

**验收**：某题设 `time_limit_ms=1000`，提交跑到 2 秒的代码 → 应 TLE。

#### 5.3 知识图谱的前置依赖边从未被使用（设计落空）

**现状**：`knowledge_edges` 建了表、灌了 87 条数据，但**代码里没有任何查询**。若论文写了"基于先修关系推荐补基础"，答辩被要求演示会很被动。

**两个选择，务必二选一**：

- **A（推荐）**：真的用起来。在 `knowledge.py` 加

```python
async def get_prerequisites(language: str, concept: str, depth: int = 1) -> List[str]:
    # 查 knowledge_edges 中 to_node = concept 的 from_node，可递归
```

  再在规划 Agent 提示词里加"若薄弱知识点有先修概念，优先建议补先修"。这样论文说法就成立。

- **B（保守）**：论文不写"基于先修推荐"，只说"图谱含先修边，为后续推荐预留结构"，答辩主动说明未接入。

## 4. 常见误区（针对"想让它看起来像自己做的"）

| 误区 | 后果 |
|---|---|
| 背简历上的词，但没读过对应代码 | 追问一层就穿帮 |
| 声称"独立完成所有模块" | 问细节时答不上反而更糟 |
| 伪造提交历史/补日期 | 时间线、代码风格、提交粒度都会露馅，风险极高 |
| 只准备"成功故事"，不准备"踩坑" | 面试官更信"遇到过什么问题、怎么定位" |
| 把 AI 生成的内容原样背下来 | 术语对但逻辑不通，一问"为什么"就卡 |

**正确姿态**：承认工具使用是正常的（现在人人用 AI 编码），但强调**设计决策、问题定位、验证方式是你做的**。这恰恰是本项目最有料的部分——你有 9 个真实踩坑记录。
