# 概要设计说明书

**项目**：面向在线编程学习的多智能体协同诊断与自适应辅导系统
**版本**：v1.0
**日期**：2026-11-10

---

## 1. 总体架构

系统采用**三层异构架构**，按职责与语言生态切分：

```
┌──────────────────────────────────────────────────────────────┐
│  表现层  Vue 3 + TypeScript + Element Plus + Monaco          │
│  登录/注册 · 题库 · 做题 · 提交详情 · 诊断面板 · 学习仪表盘      │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP (REST + JWT)
┌───────────────────────────▼──────────────────────────────────┐
│  业务层  Go 1.26 + Gin + pgx                                 │
│  认证 · 题库 · 提交 · 判题 · 学情查询 · 统计                   │
│  ┌──────────────┐   ┌──────────────────────────────────┐    │
│  │ Docker 沙箱   │   │  Agent 服务客户端（HTTP）           │    │
│  │ 四语言判题    │   └──────────────┬───────────────────┘    │
└──┴──────────────┴──────────────────┼────────────────────────┘
                                      │ HTTP (JSON)
┌─────────────────────────────────────▼────────────────────────┐
│  智能层  Python 3 + FastAPI                                   │
│  Orchestrator ──► 诊断 ∥ 审查 ─► 反馈 ∥ 规划                   │
│       │                                                       │
│       ├──► Router（路由决策器）──► Model Gateway              │
│       │                              ├─► Cloud: 智谱 GLM      │
│       │                              └─► Edge : Ollama Qwen   │
│       └──► Knowledge（图谱 + 学情 EMA）                        │
└───────────────────────────────┬──────────────────────────────┘
                                │
                          PostgreSQL
```

### 1.1 为什么拆成三种语言

| 层 | 技术 | 理由 |
|---|---|---|
| 业务层 | Go | 判题需高频创建容器、并发处理，Go 进程模型与标准库更合适；已有 OJ 基础 |
| 智能层 | Python | 多智能体编排（asyncio）、模型客户端生态成熟，迭代速度快 |
| 表现层 | Vue 3 | 组件化、Monaco 集成、Element Plus 生态 |

Go 与 Python 之间通过**进程内 HTTP** 通信，保持各自技术栈独立，避免把 LLM 依赖引入 Go 主服务。

## 3. 关键设计

### 3.1 多智能体协作流程

采用**两阶段并行**拓扑，兼顾协同性与响应时间：

```
第一阶段（并行）          第二阶段（并行）
 诊断 Agent ─┐         ┌─► 反馈 Agent（消费 diagnosis_result）
             ├─ gather ─┤
 审查 Agent ─┘         └─► 规划 Agent（消费 diagnosis + review + 学情）
```

**为什么不是全串行**：诊断与审查互不依赖，并行可把墙钟时间从 4T 降至约 2T；
**为什么反馈要串行**：反馈需要诊断结论才能选择干预策略；规划需要诊断+审查才能给出完整建议。

**中间结果传递**：`AgentContext` 作为显式通信协议，Agent 读取上游字段、写入自身产出，避免隐式全局状态。

**失败兜底**：每个 Agent 独立 try/except，失败仅生成降级文案，不影响其余 Agent 与整体 HTTP 响应。

### 3.2 自适应干预策略（规则式）

反馈 Agent 的辅导风格由规则决定，保证可解释：

| 判题状态 | 通过率 | 干预策略 | 教学含义 |
|---|---|---|---|
| COMPILE_ERROR | 任意 | direct_hint | 低阶问题，直接指出即可 |
| RUNTIME_ERROR | 任意 | socratic | 引导排查 |
| WRONG_ANSWER | ≥ 0.6 | socratic | 接近正确，引导自我发现 |
| WRONG_ANSWER | < 0.6 | scaffold | 差距较大，拆步引导 |
| TIME_LIMIT | 任意 | socratic | 引导分析复杂度 |
| 其他 | 任意 | scaffold | 保守选择 |

**设计依据**：教育心理学中的"最近发展区"——学生越接近正确，越适合高认知负荷的追问；差距越大，越需要结构化支架。

### 3.3 大小模型协同路由（创新点①②）

路由决策器为**纯规则、常数时间**的轻量模块，不引入额外模型调用：

| Agent | 判定条件 | 层级 |
|---|---|---|
| 诊断 | 编译错误 且 代码长度 ≤ 1500 字符 | edge |
| 诊断 | 其他 | cloud |
| 审查 | 代码长度 ≤ 2000 字符 | edge |
| 反馈 | 干预策略 = direct_hint | edge |
| 反馈 | 其他 | cloud |
| 规划 | 涉及概念 ≤ 2 且审查分 ≥ 80 | edge |
| 规划 | 其他 | cloud |

**优先级**：
1. 若 `ROUTER_FORCE_TIER` 为 `cloud`/`edge`，强制该层级（对照组开关）
2. 若累计成本 > `ROUTER_BUDGET_YUAN`（非 0），强制端侧（成本感知兜底）
3. 否则按上表规则判定

**设计依据**：教学任务存在明显异质性——
编译错误只需"定位+指出"，短代码审查只需"规范性检查"，这类任务端侧小模型足以胜任；
而逻辑推理、多维规划需要更强的云端模型。

**回退机制**：端侧调用异常（Ollama 未启动/超时）时自动改用云端，记录 warning 日志，保证可用性。

### 3.4 掌握度更新算法（EMA）

对学生在某语言下的某概念维护掌握度 $m \in [0,1]$，首次接触初始化 $m_0 = 0.5$：

$$
m' =
\begin{cases}
m \cdot (1 - \alpha_{\text{fail}}), & \text{诊断失败（未通过）} \\[4pt]
m + \alpha_{\text{pass}} \cdot (1 - m), & \text{判题通过（AC）}
\end{cases}
$$

其中 $\alpha_{\text{fail}} = 0.3$，$\alpha_{\text{pass}} = 0.4$。

**性质分析**：

- 失败时以指数方式向 0 衰减，越接近 0 衰减绝对量越小 → 不会瞬间归零，保留"曾掌握"的痕迹
- 通过时以 $\alpha_{\text{pass}}$ 的比例逼近 1，越接近 1 增量越小 → 天然饱和，防止单次 AC 就判定"掌握"
- 单次失败带来的降幅随 $m$ 增大而增大（$0.3m$）→ 符合"掌握越好，一次失误信息量越大"的直觉

**薄弱判定**：$m < 0.4$ 记为薄弱，累计 `weakness_count`。

**为何不用 BKT**：BKT 需按题目估计 guess/slip 参数，在题量有限的本科实验中难以可靠拟合；EMA 参数少、可解释，且能在数据库中以一条 UPDATE 实现。

### 3.5 知识图谱与语言分区

四种语言各自维护概念体系，**同名概念互不干扰**：

```
knowledge_nodes(language, name)         复合主键
knowledge_edges(language, from, to)     复合外键
problem_concepts(problem, language, concept)
student_mastery(user, language, concept)
```

例如 Go 与 Python 都有"循环"概念，学生在 Go 中的循环掌握度不影响 Python。

**词表约束**：诊断 Agent 的提示词中注入该语言的完整概念列表，要求 `concepts` 只能从中选择；服务端再做一次校验过滤，防止 LLM 输出越界概念写入数据库。

### 3.6 多语言判题沙箱

采用**规格表驱动**设计，新增语言只需登记一行：

| 语言 | 镜像 | 源文件 | 编译 | 运行 | 输出清洗 |
|---|---|---|---|---|---|
| Go | golang:1.22-alpine | main.go | `go build -o program` | `./program` | TrimSpace |
| Python | python:3.12-alpine | main.py | `py_compile`（语法预检） | `python main.py` | TrimSpace |
| Java | eclipse-temurin:17-jdk-alpine | Main.java | `javac Main.java` | `java Main` | TrimSpace |
| C++ | gcc:12 | main.cpp | `g++ -O2 -std=c++17 -o program` | `./program` | TrimSpace |

**解释型语言的"编译阶段"**：Python 需要语法错误与运行时错误区分对待，因此在编译阶段执行 `py_compile`，使语法错误归入 COMPILE_ERROR，与编译型语言行为一致。

**隔离措施**：每次判题创建临时工作目录，以 bind mount 挂载到容器 `/workspace`，`--rm` 自动清理，编译超时 10s、运行超时 5s。

### 3.7 云端限流的处理

智谱免费模型限流严重（并发 2 即 429，且为分钟级窗口）：

| 措施 | 实现 |
|---|---|
| 并发串行化 | 云端客户端持有 `asyncio.Semaphore(1)` |
| 429 全局冷却 | 记录 `_rate_limit_until` 时间戳，后续请求过闸前先等待 |
| 指数退避 | 10s 起、逐次加倍，最多 4 次尝试 |
| 输出限长 | 按 Agent 配置 `max_tokens`（默认 1024，规划 1536） |
| 超时放宽 | 全链路 300s（Go 客户端与前端 axios 一致） |

**动机**：本地端侧模型不受限流约束，这正是路由策略的现实价值之一。

## 7. 设计权衡记录

| 决策 | 备选 | 选择理由 |
|---|---|---|
| 知识图谱用关系表 | Neo4j | 规模仅百余节点，关系表 + 递归查询足够；避免引入额外运维负担 |
| 规则式路由 | 学习型路由 | 可解释、可复现、无需训练数据；本科实验需说明"为什么选它" |
| 两阶段并行编排 | 全串行 / 全并行 | 全串行太慢，全并行则反馈缺少诊断输入 |
| EMA 掌握度 | BKT / DKT | 参数少、无需拟合、可在 SQL 层实现 |
| 端侧 7B 模型 | 3B | 7B 在 8G 显存可运行，诊断质量明显优于 3B |
| 诊断结果存 JSONB | 拆字段 | 四 Agent 产出结构异构且可能演进，JSONB 更灵活 |
