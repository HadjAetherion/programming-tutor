# 需求规格说明书

**项目**：面向在线编程学习的多智能体协同诊断与自适应辅导系统
**版本**：v1.0
**日期**：2026-11-10

---

## 1. 引言

### 1.1 编写目的

本文档明确系统的功能需求、非功能需求、数据需求与约束条件，作为系统设计、实现与验收的依据。读者对象为：指导教师、评审专家、系统开发者与测试者。

### 1.2 项目背景

在线编程学习平台（OJ）已能完成"提交—判题—判定对错"，但**判题结果本身不具教学价值**：学生只知道"答案错误"，不知道错在哪、为什么错、下一步该学什么。现有基于大语言模型的辅导方案存在两个现实矛盾：

1. **成本与延迟**：每次辅导都调用云端大模型，免费额度限流严重、响应动辄数十秒，难以支撑高频提交场景；
2. **缺乏个性化**：模型不知道学生历史薄弱点，辅导建议"千人一面"。

本系统在判题链路之后引入**多智能体协同诊断**，并通过**大小模型协同路由**在成本、延迟与质量之间取得平衡。

### 1.3 术语定义

| 术语 | 说明 |
|---|---|
| OJ | Online Judge，在线判题系统 |
| Agent | 承担单一教学职责的 LLM 智能体 |
| 端侧模型 | 本地部署的小参数模型（Ollama + Qwen2.5-7B） |
| 云端模型 | 通过 API 调用的云服务大模型（智谱 GLM-4.7-Flash） |
| 路由决策器 | 决定某次推理任务使用端侧还是云端的轻量模块 |
| 掌握度 | 学生对某知识点的能力估计值（0~1），EMA 更新 |
| 干预策略 | 反馈 Agent 采用的辅导风格（直接提示/苏格拉底式/分步引导） |

## 2. 总体描述

### 2.1 产品定位

面向**程序设计入门课程**的教学辅助平台。学生在平台上做题；提交未通过时，系统自动触发多智能体诊断，生成诊断结论、辅导反馈、代码审查与学习规划；学习仪表盘呈现掌握度与推理成本。

### 2.2 用户角色

| 角色 | 特征 | 主要诉求 |
|---|---|---|
| 学生（主要用户） | 程序设计入门学习者 | 知道错在哪、怎么改、下一步学什么 |
| 教师（观察者） | 课程教师 / 实验组织者 | 了解班级学习状况、组织实验 |
| 系统管理员（实验组织者） | 部署者 | 配置模型、分组、导出实验数据 |

### 2.3 运行环境

| 项 | 要求 |
|---|---|
| 服务端 | Windows / Linux，Go 1.21+、Python 3.9+、PostgreSQL 14+、Docker |
| 端侧模型 | Ollama，建议 8GB 显存以上的 GPU（实测 RTX 4060 Laptop） |
| 客户端 | 现代浏览器（Chrome / Edge / Firefox 最新版） |

### 2.4 设计约束

- C1：判题必须隔离执行用户代码（容器沙箱），不得在宿主机直接运行
- C2：所有模型密钥通过环境变量注入，不得硬编码或入库
- C3：云端模型存在限流与配额约束，系统必须能在限流下优雅降级
- C4：知识图谱规模有限（四语言、每语言 20~30 概念），直接以关系表实现，不引入图数据库

## 3. 功能需求

### FR-1 用户与认证

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-1.1 | 学生可注册账号（用户名、邮箱、密码），邮箱唯一 | 必须 |
| FR-1.2 | 学生可登录，获得 JWT 令牌访问受保护接口 | 必须 |
| FR-1.3 | 前端提供注册页与登录页，注册成功后自动登录 | 必须 |
| FR-1.4 | 任意页面可退出登录 | 必须 |

### FR-2 题库与判题

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-2.1 | 以卡片列表展示题目（标题、难度、描述） | 必须 |
| FR-2.2 | 题目详情页展示描述、输入/输出说明、约束、样例 | 必须 |
| FR-2.3 | 支持 Go / Python / Java / C++ 四种语言作答 | 必须 |
| FR-2.4 | 支持"运行代码"（自定义输入）与"提交判题"（跑全部测试用例） | 必须 |
| FR-2.5 | 判题结果区分 ACCEPTED / WRONG_ANSWER / COMPILE_ERROR / RUNTIME_ERROR / TIME_LIMIT | 必须 |
| FR-2.6 | 记录每次提交的通过用例数与总用例数 | 必须 |
| FR-2.7 | 展示当前题目的提交历史，并标记"已诊断" | 建议 |

### FR-3 多智能体诊断辅导

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-3.1 | 提交未通过时自动触发诊断，异步展示，不阻塞判题结果 | 必须 |
| FR-3.2 | 诊断 Agent 输出错误类型、根因、涉及知识点、讲解、提示 | 必须 |
| FR-3.3 | 反馈 Agent 按干预策略生成辅导内容与引导问题 | 必须 |
| FR-3.4 | 审查 Agent 输出质量评分、亮点、问题清单（不泄露正确解法） | 必须 |
| FR-3.5 | 规划 Agent 输出学习步骤与下一题建议 | 必须 |
| FR-3.6 | 四个 Agent 中任一失败不得中断其余 Agent，需降级展示 | 必须 |
| FR-3.7 | 诊断结果持久化，可通过只读接口重新查看 | 必须 |
| FR-3.8 | 辅导内容不得直接给出完整正确代码 | 必须 |

### FR-4 大小模型协同（创新点①②）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.1 | 路由决策器按「Agent 角色 × 任务特征 × 上下文复杂度」选择推理层级 | 必须 |
| FR-4.2 | 路由规则可解释、可配置（规则表形式） | 必须 |
| FR-4.3 | 端侧调用失败时自动回退云端 | 必须 |
| FR-4.4 | 支持强制全云端开关（`ROUTER_FORCE_TIER`），用于对照组 | 必须 |
| FR-4.5 | 支持成本预算兜底（`ROUTER_BUDGET_YUAN`） | 建议 |
| FR-4.6 | 每次调用记录角色、层级、模型名、延迟、Token、成本 | 必须 |

### FR-5 知识图谱与学情（阶段 4）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-5.1 | 维护四种语言各自的概念节点与前置依赖边 | 必须 |
| FR-5.2 | 诊断输出的知识点必须限定在该语言概念词表内 | 必须 |
| FR-5.3 | 诊断命中知识点时自动累积题目—概念标注 | 必须 |
| FR-5.4 | 诊断失败时对涉及概念执行掌握度衰减 | 必须 |
| FR-5.5 | 判题通过时对题目标注概念执行掌握度增强 | 必须 |
| FR-5.6 | 掌握度低于阈值记为薄弱，并累计薄弱次数 | 建议 |
| FR-5.7 | 规划 Agent 读取学生薄弱知识点作为输入 | 必须 |

### FR-6 学习仪表盘（创新点③）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-6.1 | 展示 AI 调用总次数与端侧调用占比 | 必须 |
| FR-6.2 | 展示端侧/云端平均延迟（按调用次数加权） | 必须 |
| FR-6.3 | 以排名条形图展示知识点掌握度，最薄弱在前 | 必须 |
| FR-6.4 | 掌握度支持按语言筛选 | 建议 |
| FR-6.5 | 按 Agent 角色分组展示端侧与云端延迟对比 | 必须 |
| FR-6.6 | 提供调用明细表（次数/平均延迟/Token/成本） | 必须 |

### FR-7 实验支撑

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-7.1 | 提供题库（20~30 题）与配套测试用例 | 必须 |
| FR-7.2 | 提供前后测平行卷与 NASA-TLX 问卷 | 必须 |
| FR-7.3 | 提供分组、成绩、问卷数据录入手段 | 必须 |
| FR-7.4 | 提供统计脚本，输出分组对比与效应量 | 必须 |

## 4. 非功能需求

### NFR-1 性能

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-1.1 | 编译错误类提交的诊断响应 | ≤ 15 s（端侧路径） |
| NFR-1.2 | 完整四 Agent 流程墙钟时间 | ≤ 300 s（云端限流下） |
| NFR-1.3 | 判题单次执行超时 | 5 s；编译超时 10 s |
| NFR-1.4 | 页面首屏（题库列表）加载 | ≤ 3 s（局域网） |

### NFR-2 可靠性

| 编号 | 需求 |
|---|---|
| NFR-2.1 | 单一 Agent 失败不导致整体不可用，需有降级文案 |
| NFR-2.2 | 端侧服务不可用时自动路由到云端 |
| NFR-2.3 | 云端限流（429）时需有全局冷却与重试，不得空转 |
| NFR-2.4 | 数据库不可用时诊断主流程仍可运行（成本日志降级） |

### NFR-3 安全性

| 编号 | 需求 |
|---|---|
| NFR-3.1 | 用户代码在 Docker 容器内执行，限制运行时长与工作目录 |
| NFR-3.2 | 密钥仅存于 `.env`，不纳入版本控制 |
| NFR-3.3 | 所有业务接口需 JWT 鉴权，且只能访问本人数据 |
| NFR-3.4 | 密码以 bcrypt 哈希存储 |

### NFR-4 可维护性

| 编号 | 需求 |
|---|---|
| NFR-4.1 | 后端分层：handler → service → repository |
| NFR-4.2 | 新增编程语言只需登记沙箱语言规格表与知识图谱节点 |
| NFR-4.3 | 新增 Agent 只需实现统一基类并注册到编排器 |

### NFR-5 可用性

| 编号 | 需求 |
|---|---|
| NFR-5.1 | 提供一键启动脚本 |
| NFR-5.2 | 全站中文界面，任意页面可返回上一级或退出发登录 |
| NFR-5.3 | 图表提供颜色之外的第二编码（标签/表格），保证色觉障碍可读 |

## 5. 数据需求

### 5.1 核心实体

| 实体 | 说明 |
|---|---|
| User | 用户（学生） |
| Problem | 题目 |
| ProblemTestCase | 测试用例（输入/期望输出/是否样例） |
| Submission | 提交记录（代码/语言/状态/用例通过数） |
| SubmissionDiagnosis | 诊断结果（四 Agent 产出 + 调用元信息） |
| LLMCallLog | 单次模型调用日志（角色/层级/模型/延迟/Token/成本） |
| KnowledgeNode / KnowledgeEdge | 知识概念与前置依赖（按语言分区） |
| ProblemConcept | 题目—概念标注（按语言，含命中次数） |
| StudentMastery | 学生掌握度（按语言与概念唯一） |
| ExperimentGroup / AssessmentScore / NasaTLX | 实验数据 |

### 5.2 数据保留与隐私

- 仅采集学习行为数据：提交代码、判题结果、诊断结果、问卷评分
- 论文与报告中所有数据匿名化（以 ID 呈现）
- 参与者签署知情同意，可随时退出并删除数据

## 6. 验收标准

系统通过验收需同时满足：

1. 四种语言均可正常判题且结果准确（题库全部参考解 AC）；
2. 未通过提交能触发四 Agent 诊断，结果完整展示且持久化；
3. 路由决策器在真实调用中生效（日志可见端侧/云端混合），端侧故障可回退；
4. 诊断失败后学生掌握度下降，判题通过后上升；规划内容引用薄弱知识点；
5. 仪表盘正确呈现掌握度与端云成本/延迟对比；
6. 一键启动可拉起全部三个服务；
7. 代码库不含任何明文密钥。
